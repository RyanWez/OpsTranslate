Request Lifecycle & Gate Order

EVERY MESSAGE PASSES THESE 10 GATES IN ORDER
Why the order matters

Only Gate 10 costs money. Every cheap, deterministic check (identity, length, language, duplicate, rate) sits in front of it, so that a rejected request returns instantly and spends nothing. Rate limiting after the AI call is the most common expensive mistake.

Inside Gate 10 — the pipeline

a
Normalise

Unicode NFC · collapse repeated whitespace · strip zero-width characters. Zawgyi is out of scope — see Appendix A for the 15-line emergency patch if it ever appears.

b
Protect entities

URLs, @mentions, numeric IDs, 12345678-style account numbers and /commands are swapped for inert placeholders of the form ⟦E:url:1⟧, ⟦E:id:2⟧, … — a separate namespace from the term-policy ⟦T:concept⟧ placeholders — so they survive untouched and are restored verbatim after translation. The system prompt documents both namespaces; the render step only ever substitutes ⟦T:…⟧, and entity placeholders are restored afterwards, never rendered.

c
Mask sensitive vocabulary Layer 2

Longest-match-first scan replaces every term-policy hit with ⟦T:concept⟧. The provider never sees the original word. This is the layer that actually guarantees the rule.

d
Build prompt Layer 1

Static system prompt (cacheable) + policy block listing each placeholder and its meaning + few-shot examples. User text is wrapped in <src>…</src> delimiters.

e
Translate with failover

Brain AI (priority 1) → backup 2 → backup 3. Circuit breaker opens after 5 consecutive failures, half-opens after 60 s. Concurrency capped by a semaphore of 8.

f
Render placeholders Layer 2

⟦T:balance⟧ → “Amount” in English and “ပမာဏ” in Myanmar.

g
Deny-scan & repair Layer 3

Scan the output for forbidden terms in the target language. On a hit: retry once with a stricter suffix. On a second hit: send nothing, log, alert.

h
Sanity checks

Output/input length ratio must fall between 0.3× and 3.0×. Meta-responses (“As an AI…”, “I cannot…”) are rejected. Both catch prompt-injection and model collapse cheaply.

i
Deliver & log

Restore entities, send as a reply to the source message, write the metadata-only log row.

Delivery: placeholder → edit

Because the response is one short message, delivery is two API calls:

# 1. immediate acknowledgement, anchored as a reply
ph = await bot.send_message(
    chat_id, "⏳ Translating…",
    reply_parameters=ReplyParameters(
        message_id=src.message_id,
        allow_sending_without_reply=True,
    ),
)

# 2. replace it with the finished translation
await bot.edit_message_text(
    chat_id=chat_id,
    message_id=ph.message_id,
    text=result,
)

⚠️ The reply anchor must be set on call 1. editMessageText cannot add a reply relationship afterwards — if you skip it on the first call you cannot recover it.

Streaming is not needed in this build

With a 250-character cap the round trip is 0.8–1.5 s. Token-by-token streaming would add throttle state, draft-lifecycle bugs and duplicate-message edge cases for a benefit nobody can perceive. It is documented in Appendix B if you ever want it for long inputs.

04

Term Policy Engine

THE REASON THIS BOT EXISTS
Design principle

An instruction in a prompt is a request. A substitution applied before the model sees the text is a guarantee. Staff will always type the real words — “game ID”, “game account”, “game points” — and the bot must neutralise them silently and every single time. That is only reliable if the sensitive word is removed from the model's input entirely and re-inserted afterwards from a table you control.

4.1 — Three layers of defence

LAYER 1 — REQUEST

Prompt instruction

A short policy block plus 2–3 few-shot examples in the system prompt. Raises compliance, but is never trusted alone.

LAYER 2 — GUARANTEE ⭐

Placeholder masking

Sensitive terms become ⟦T:concept⟧ before the request leaves the server. The model cannot reproduce a word it never received.

LAYER 3 — PROOF

Deny-scan & repair

The finished output is scanned against forbidden terms in the target language. On a hit: one stricter retry, then withhold.

Matching rules that will otherwise bite you

1. Longest-match-first. “ဂိမ်းပွိုင့်” must match before “ဂိမ်း”, or the compound breaks into a mapped fragment plus an orphan word.

2. Word boundaries for English only. Use \b around English patterns so “gamer” is not split by the “game” rule. Myanmar has no spaces — use plain substring matching there.

3. Case-insensitive for English. re.IGNORECASE. Irrelevant for Myanmar.

4. Deny lists are per target language. Scanning an English output with Myanmar words finds nothing. Maintain both lists.

5. Over-mapping is a real risk. “points” in a non-sensitive sentence is still mapped — acceptable here because the mapping is neutral, not wrong. Keep concept keys narrow and review new ones weekly.

4.3 — Implementation

Mask & render

PLACEHOLDER = re.compile(r"⟦T:([a-z_]+)⟧")

def mask(text: str, src: str, policy) -> str:
    """Sensitive source terms → ⟦T:concept⟧ before the AI sees them."""
    for pattern, concept in policy.matchers(src):   # longest first
        text = pattern.sub(f"⟦T:{concept}⟧", text)
    return text

def render(text: str, dst: str, policy) -> str:
    """⟦T:concept⟧ → approved neutral term in the target language."""
    def _sub(m):
        return policy.output(m.group(1), dst)   # approved rows only
    return PLACEHOLDER.sub(_sub, text)

def deny_scan(text: str, dst: str, policy) -> list[str]:
    """Layer 3: forbidden terms in the OUTPUT language."""
    haystack = text.casefold()
    body = policy.deny_list(dst)          # e.g. en: game, slot, casino,
    return [w for w in body if w.casefold() in haystack]  # betting…

At 250-character inputs this is microseconds. Only switch to pyahocorasick if the policy ever exceeds a few thousand patterns.

Pipeline with repair loop

async def translate_policied(text, src, dst, policy):
    masked = mask(protect_entities(text), src, policy)
    prompt = build_prompt(src, dst, policy)      # Layer 1

    out, provider = await router.translate(masked, prompt)

    for attempt in (1, 2):
        if not ratio_ok(text, out) or is_meta_response(out):
            out, provider = await router.translate(
                masked, prompt, force=provider)
            continue

        rendered = render(out, dst, policy)      # Layer 2 post
        leaks = deny_scan(rendered, dst, policy) # Layer 3
        if not leaks:
            return restore_entities(rendered), provider

        log.warn("policy_leak", leaks=leaks, provider=provider,
                 policy=policy.version)
        out, provider = await router.translate(
            masked, prompt + strict_suffix(leaks), force=provider)

    await alert.policy_failure(policy.version)
    raise PolicyRefusal()          # withhold — never ship a leak
Make this the default, not an option

If the deny-scan still fires after one repair attempt, send nothing. Withholding a translation costs one annoyed user; shipping a leaking translation costs you the reason the bot was built.

4.5 — Policy governance

  • Versions are mandatory. Every rule change publishes a new policy_version, and every log row records which version produced it.
  • One-click rollback. If v8 misbehaves, re-point to v7 and the change is live within 60 s without redeploy.
  • Regression set of 40 cases. Real examples covering each concept, each language pair, mixed-language inputs (Burmese + English in one message — the normal case), and known traps. A version cannot be published unless all 40 pass.
  • Single owner. One or two admins may edit policy; every edit writes an audit row with before/after values.
  • Weekly leak review. Any policy_leak event becomes a new deny term or a new variant within a week.

4.6 — Known limitations (accept these consciously)

  • Meaning is diluted by design. “Game points” → “Balance” loses specificity. The trade is intentional.
  • Very short input is the hard case. A bare “gid?” carries no context — an ID-format placeholder removes some of this, but not all.
  • New slang reaches production first. Layer 3 catches it in the output, which is why the leak log exists.
  • Each new provider needs a prompt re-test. Instruction-following quality differs between models; the regression set is run against every provider before it goes live.
  • Proper nouns are untouched. Brand and product names pass through unchanged unless you explicitly add them to the policy.

The 250-Character Cap — Analysis and Recommendation

SHOULD IT BE 250, 150 OR 100?
Recommendation
Keep 250
Do not cut to 150 or 100. Revisit with two weeks of real data instead of guessing.

CapWhat it rejectsConsequenceVerdict
100 Any two-sentence message, any pasted paragraph Staff hit the wall several times a day, start splitting messages, and the tool feels broken. Compliance drops. Too aggressive
150 Three-sentence complaints, multi-line pastes from a customer chat Workable but still interrupts real work. Gains almost nothing: 150 vs 250 changes neither cost nor latency meaningfully. Unnecessary

The real value of the cap — it deletes complexity

At 250 characters the output is always one Telegram message (a 250-character English input can expand to roughly 400–700 Myanmar characters, still far below the 4,096 limit). That single fact removes an entire category of work: no message splitting, no chunk resend logic, no document fallback, no streaming, no partial-failure recovery, no long-request timeouts. Keep the cap and you delete roughly a day of engineering and its bug surface.

How to count, and how to reject

  • Count the raw source text with len(text) on the string as received, before masking, before normalisation. That is the number the user sees.
  • Do not cap the masked text. Masking can inflate length — “ဂိမ်းအကောင့်” (12 chars) becomes ⟦T:user_account⟧ (18 chars). The cap is a user-facing rule, not a pipeline rule.
  • Reject with the count visible: "Message is too long — 312 / 250 characters. Please split it and send again." Never silently truncate — truncating changes meaning, and meaning is the entire product.
  • Never challenge the check: the rejection happens at Gate 5, before the rate limit is consumed, so a user who over-lengths a message does not lose a rate slot for it.
  • Store the cap in the DB as settings.max_input_chars. Adjust it in the dashboard, live.

Decide with data, not instinct

The usage_log already stores char_len for every accepted message (no text, no content — just the number). After two weeks you will be able to answer this properly:

-- Distribution of real message lengths
SELECT width_bucket(char_len, 0, 250, 10) AS bucket,
       count(*), round(avg(latency_ms)) AS avg_latency
FROM usage_log
WHERE ts > now() - interval '14 days' AND status = 'ok'
GROUP BY 1 ORDER BY 1;

-- How often did anyone actually hit the ceiling?
SELECT count(*) FILTER (WHERE status = 'too_long') * 100.0 / count(*) AS pct_rejected
FROM usage_log WHERE ts > now() - interval '14 days';

If pct_rejected is under ~2%, the cap is correct where it is. If it is over 10%, the cap is the problem and you should raise it, not lower it. Lowering it further is the one change that is almost certainly wrong.

Rate Limiting — 2 Messages per Rolling 30 Seconds

SLIDING WINDOW, IN-PROCESS
from collections import defaultdict, deque

WINDOW, LIMIT = 30.0, 2
_hits: dict[int, deque[float]] = defaultdict(deque)

def rate_check(user_id: int, now: float) -> int:
    """Return 0 if allowed, else the seconds the user must wait."""
    q = _hits[user_id]
    while q and now - q[0] >= WINDOW:
        q.popleft()                      # evict entries outside the window
    if len(q) >= LIMIT:
        return max(1, math.ceil(WINDOW - (now - q[0])))
    q.append(now)
    return 0
  • Sliding, not bucketed. A fixed 30-second bucket would let a user send 2 messages at second 29 and 2 more at second 31 — four in three seconds.
  • In-process, not Redis. Single instance, ≤120 users: an in-memory deque is faster, needs no network round trip, and — critically — consumes zero Upstash commands. The Redis free tier is 500 K commands per month; rate limiting through Redis would burn a large share of it for no benefit. Swap in a Redis Lua script only if you ever run two instances.
  • Consume the slot after gates 1–7. A rejected message must never cost a slot.
  • Admin bypass via the role column in allowed_users.
  • The countdown reply itself must not consume a slot, or a user could lock themselves into a loop of countdowns.

Duplicate handling (Gate 7) — the part that removes real friction

Staff paste the same sentence twice while switching between apps. With a naive implementation the second paste costs a rate slot and returns a second identical message.

StateAction
Identical text, target and user within 30 s, still in flightDrop silently. One response, one slot.
Identical, already answeredResend the cached translation immediately. No rate slot consumed, no provider call.
Same text after 30 sNormal path — served from cache (Gate 9), still consumes a slot.
Break-even check for 120 users

Worst case is 120 × 2 = 8 messages/second. Telegram's private-chat ceiling is around 30/second, and a single Koyeb instance with a semaphore of 8 concurrent provider calls handles this comfortably. No queue, no worker pool, no load balancer is required at this scale.

Alerting — Telegram Only

INCLUDING THE CASE WHERE THE BOT ITSELF IS DEAD
The obvious flaw in Telegram-only alerting

If the alert sender is the bot, and the bot is the thing that is down, the alert never arrives. Telegram-only is a perfectly good decision — but it needs two independent paths, not one. Internal alerts come from the app; external alerts come from an uptime monitor that is not the app.

Path A — Internal alerts (from the running bot)

The app posts to the admin's Telegram chat using a separate alert bot token, not the user-facing bot. Keeping them separate means a token problem in the user bot cannot silence alerts, and it keeps alert traffic out of the working chat.

P1All providers down · DB unreachable · Redis unreachable · policy engine raising on >20% of requestsImmediate, then 15 min per fingerprint
P2One provider circuit-opened · error rate >5% over 5 min · p95 latency >4 s · policy_leak event · daily spend cap reached15 min per fingerprint
P3Daily digest 09:00 Asia/Yangon · weekly policy-review reminder · new /whoami request from an unknown userOnce per day

Alert hygiene — the difference between monitoring that works and monitoring that is muted

  • Fingerprint every alert as {type}:{component}. Repeat events inside the cooldown increment a counter instead of sending a new message.
  • Always send a resolution. When the circuit closes or the check recovers, send a short recovered message with duration. Unresolved alerts train people to ignore alerts.
  • Cap the volume at 20 alerts per hour. Beyond that, send one summary line instead.
  • Every alert must be actionable — one line stating what to do next, not just what broke.
  • Never include message text in an alert. Concept keys, counts, provider names and policy versions only — the no-storage privacy guarantee extends to the alert channel.

Path B — External alerts (dead-man's switch)

An uptime monitor polls /healthz every 5 minutes and posts to Telegram when the check fails. Both UptimeRobot and BetterStack support Telegram as a notification channel on their free tiers. This is the only path that survives the bot being dead.

Make /healthz a real check, not a liveness stub

@app.get("/healthz")
async def healthz():
    checks = {
        "db":    await db.ping(),
        "cache": await redis.ping(),
        "policy": policy.loaded and not policy.stale(),
        "provider": await breaker.any_closed(),
        "traffic":  last_success_within(seconds=600),
    }
    ok = all(checks.values())
    # 503 on degraded → the uptime monitor raises it
    return JSONResponse(checks, status_code=200 if ok else 503)

The traffic key is what makes this a real health check: a process can be alive, serve 200 OK, and still be silently failing every translation. Guard it against quiet hours — nobody using the bot at 3 AM is normal, not an outage. Implement it as last_success_within(600) or outside_working_hours() (working hours 08:00–22:00 Asia/Yangon), so a silent failure pages the admin during the day but never at night.

Keep-warm is not the same job

Separately, a GitHub Actions cron pings /healthz every 5 minutes to keep Neon from suspending. That is a latency optimisation, not monitoring — keep the two concerns distinct so a monitor failure does not silently degrade latency.

Optimisations for the Final Build

WHAT ELSE IS WORTH DOING — RANKED
01
Delete chunking, streaming and document handling entirely −1 day
The 250-character cap means the output always fits one message. This removes the single largest source of edge cases in a translation bot. Do this first — it is a deletion, not a feature.
02
Load policy, prompts and the provider list into memory at boot 2 h
Nothing in the hot path should touch Postgres. Load once at startup, then poll a single version row every 60 s; reload on change. Combined with keep-warm this removes the Neon cold-start penalty from the user's experience.
03
Per-language deny lists + an output/input length ratio check 3 h
Scanning English output with Myanmar words finds nothing. And a ratio outside 0.3×–3.0× reliably catches model collapse, prompt injection and “As an AI assistant…” refusals — a deterministic guard that costs microseconds.
04
Wrap user text in delimiters and refuse meta-responses 1 h
Staff will paste text that contains “ignore previous instructions” — customers write strange things. Delimiters plus a meta-response reject make injection a non-event, since the system prompt is fixed and the output is scanned anyway.
05
Enable provider prompt caching on the static system prompt 2 h
The system prompt is identical on every one of ~2,400 daily requests. If Brain AI supports prefix caching, this alone cuts input token cost substantially with no quality change.
06
Normalise the cache key to raise the hit rate 1 h
Casefold, collapse whitespace, convert full-width punctuation before hashing. “How do I check my balance?” and “how do i check my balance?” currently miss each other. Every extra point of cache hit rate is a direct cost reduction. Entries expire after 7 days; publishing a new policy version invalidates stale entries immediately (the key already includes policy_version).
07
Cap provider concurrency with a semaphore of 8 30 min
Protects the 512 MB container from a burst of simultaneous slow requests, keeps p95 latency predictable, and avoids tripping the provider's own rate limit during a failover storm.
08
Hard spend cap with automatic degrade to cache-only 3 h
A daily counter in Redis, checked before Gate 10. Over the cap: serve from cache, reply with the generic error, and raise a P2 alert. This is what stops a runaway loop from becoming a surprise invoice.
09
Per-user daily soft cap (default 200 messages) 1 h
The 2/30s limit bounds rate but not volume. A soft daily cap with an admin override catches the single user who pastes an entire document in twenty pieces.
10
Alert fingerprinting, cooldowns and resolution messages 3 h
Alert fatigue is the reason monitoring gets muted, and muted monitoring is worse than none. Fingerprint + cooldown + auto-resolve turns alerts into something the admin actually reads.
11
Explicit latency budget: 8 s provider timeout, 12 s handler budget 1 h
The user must always receive something. On budget expiry, edit the placeholder to the generic error rather than leaving “⏳ Translating…” on screen forever — a stuck placeholder is the worst possible outcome.
12
Withhold rather than ship a leak included
If the deny-scan fires twice, send nothing and alert. A missing translation is recoverable; a leaking one is not.
13
Log the character-length histogram you will need later 1 h
Storing char_len and a too_long status costs nothing and settles the 250-vs-150 question with evidence in two weeks.
14
Plain-text reply mode with disallowed link previews 15 min
Send translations with no parse mode and link_preview_options.is_disabled = true. Translating Markdown often produces broken markup, and a link preview under a short translation is pure clutter. Add formatting only if real usage demands it.
15
Backup and restore drill 4 h
Nightly pg_dump to Cloudflare R2 with 30-day retention, plus a restore actually performed once before go-live. An untested backup is a hope, not a backup.
16
One-command secret rotation and encrypted provider keys 3 h
Provider keys encrypted at rest with a key held in the platform's secret store, shown masked in the dashboard, and rotatable without redeploy. The bot token in particular should be assumed leakable and rotatable in under five minutes.
If you only do three

01 (delete the long-input machinery), 02 (in-memory policy and config), and 03 (per-language deny lists + ratio check). Together they remove the most code, the most latency and the most risk for about a day of work.

Sizing check

Memoryaiogram + FastAPI + fastText ≈ 150–250 MB against a 512 MB limit ✓
Volume~2,400 messages/day at peak 8 msg/s ✓
UpstashCache get/set + idempotency ≈ 5–7 K commands/day, well under the ~16 K/day allowance ✓
Neon storage~400 bytes per log row, no message text → ~1 MB/day; 0.5 GB lasts over a year ✓
Provider spend~$0.0004 per message at a 61% cache hit rate → roughly $2–4/month

One instance, one database, one cache. No load balancer, no queue, no worker pool.

Free-tier risks, stated plainly

  • Neon cold start — mitigations are already in the design: keep-warm cron plus in-memory policy/config so no request touches Postgres.
  • Koyeb free terms can change. If sleep is introduced, the fallback is a €4–5/month VPS, which also removes the free-tier ceiling entirely.
  • Free tiers carry no SLA. Acceptable for an internal tool — but if operations genuinely cannot tolerate downtime, budget €4–5/month for a small VPS and stop relying on free tiers for availability.
  • You own backups. Free database tiers do not guarantee retention; the nightly dump is not optional.

Two Optional Touches

ENABLE ONLY IF USEFUL

📋 Copy button (1 line — recommended)

The workflow is paste-in / paste-out. A single tap to copy beats selecting text on a phone, and it costs one keyword argument:

from aiogram.types import CopyTextButton

reply_markup = InlineKeyboardMarkup(inline_keyboard=[[
    InlineKeyboardButton(text="Copy",
                         copy_text=CopyTextButton(text=result))
]])

This is the one button worth keeping in an otherwise button-free interface. Note that copy_text takes the translated string itself, so the button holds no state.

📝 Bad-translation reporter

Instead of a thumbs-up/down pair, keep one small escape hatch: a /report command that records the last translation's usage_log row ID as flagged. Quality problems get surfaced without asking staff to rate every message — and the log row already has the policy version, provider and latency needed to diagnose it.

Deliberately not included by default: reactions, feedback buttons, retry, swap and text-to-speech. Each one adds state and UI to a tool whose entire value is speed.

Appendix A — Zawgyi emergency patch

Only if the problem actually appears. Do not enable this pre-emptively: the detector has false positives on correct Unicode text, and a false positive destroys a message that was fine.

# pip install myanmar-tools
from myanmar_tools import ZawgyiDetector, ZawgyiConverter

_det, _conv = ZawgyiDetector(), ZawgyiConverter()

def fix_if_zawgyi(text: str) -> tuple[str, bool]:
    if _det.detect(text) < 0.95:      # threshold set high on purpose
        return text, False
    return _conv.zawgyi_to_unicode(text), True

# three lines in the handler, then watch the counter:
#   text, was = fix_if_zawgyi(text)
#   if was: log.info("zawgyi_detected", user_id=uid)
# If the counter stays at zero for a month, delete the patch again.

Run the regression set immediately after enabling — this patch alters Myanmar text before the policy engine sees it.

Appendix B — Draft streaming, if long inputs ever return

Not part of this build. If it is ever needed, this is the pattern that avoids the two known failure modes.

THROTTLE_MS = 300

async def stream_draft(chat_id, deltas):
    draft_id = rand_nonzero_int()          # stable per run
    buf = last = ""; last_at = 0.0; stopped = False

    async for piece in deltas:
        buf = piece                        # OVERWRITE, never append
        now = time.monotonic()
        if stopped or now - last_at < THROTTLE_MS / 1000:
            continue                       # time throttle
        if buf == last:
            continue                       # dedupe
        try:
            await bot.send_message_draft(chat_id=chat_id,
                                        draft_id=draft_id, text=buf)
            last, last_at = buf, now
        except TelegramError:
            stopped = True; break        # stop, never retry

    await flush_and_stop(chat_id, draft_id)  # stop FIRST
    await bot.send_message(chat_id, final)   # then final

sendMessageDraft has been available to all bots since Bot API 9.5 (1 March 2026) and produces no notification and no “edited” tag. Stop the draft before sending the final message, or the final message arrives twice.
